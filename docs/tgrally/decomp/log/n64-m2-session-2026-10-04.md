Levers, measured with probe files (scratch probe.py: compile a .c with tools/ido53 and disassemble):
- **Commutative FP op operand order is NOT source order when one side is a memory load.** IDO prints a stack-array element (`s[2]`, ILOD) first whatever the source says; a volatile scalar also goes first. A coloured var + coloured var, or coloured var + an address-taken scalar/struct member (plain LOD), keeps the WRITTEN order. So ROM `add.s fd, f<coloured>, f<ring-load from sp>` = the stack value is an address-taken struct/scalar, not an array: `BrVec3 s; BrVec3 *p; ... p = &s;` (dead address-of still keeps s in memory). A CSE'd expression (d*d) is ordered like a var.
- Two loads `a + b` from memory: ugen loads a first, prints b first; flip source to flip the load order.
- `k = C; k *= m;` instead of `k = C * m;` fixes the constant/mass ring-temp order (operand swap of C*m is inert).
- Tie on save between a var web and a load-expression web: a dead early `k = b->d;` (before the switch) numbers the load web first (same lever as BrPaintDashRect's dead store).
