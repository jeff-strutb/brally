# Lane 3975de7b - proven this session

## Unrolled scale matrix: fld sx, integer sy/sz, xor-zero the rest

Construct: assign `m[0][0]=sx` first so it takes `fld`/`fstp`; `m[1][1]=sy` and
`m[2][2]=sz` become `mov r,[esp+disp]; mov [eax+off],r`. Then 12 integer zeros
in address order skipping those three plus m[3][3], which is imm `0x3f800000`.

A nested zeroing loop is `rep stosd` (45 B vs orig 70).

Distinguisher: orig `mov edx,sy; fld sx; mov [eax+0x14],edx; mov edx,sz;
fstp [eax]; xor ecx,ecx; mov [eax+0x28],edx`. Recomp after unroll matches
that except sy in ecx vs edx and sz loaded before the sy store (REGNORM 0+0,
BrMat4Scale 0x1002A7A0, 70 B).

## Degenerate frustum is `return printf(str)` not `return 1`

Orig fail path: `push "Error: guFrustumF(): unable to compute matrix\n";
call [__imp_printf]; add esp,4; ret`. eax is printf's return. `return 1`
emits `mov eax,1`. String includes the trailing newline (BRGlide 0x100a9e80).

Distinguisher: orig `push I; call [I]; add esp,4` vs missing that trio
(BrMat4Frustum 0x10029EC0). After adding it, residue is one `fxch` (x87 DAG).

## Commutative fadd/fmul operand order is not source-reachable

`pA->x += pB->x` vs `pA->x = pB->x + pA->x` both emit `fld [eax]; fadd [ecx]`
or the reverse independently of mention order. Same for `s * pB->x + pA->x`
vs `pA->x + pB->x * s` (BrVec3AddTo / MulAdd / MulAddTo / Scale / ScaleBy /
Cross). Documented wall class.
